# Sprint Planning Platform Architecture

- The platform is built around a template engine that allows participants to define their own sprint planning regimens and customize which steps are included in a session.

- A contract enforcer using the A2A (Agent-to-Agent) protocol ensures agents understand the platform's endpoints and can communicate compatibly with the system.

- A phase orchestrator reads steps from the template engine output (defined via YAML schemas) and ensures agents and participants follow the prescribed session flow.

- The session manager tracks multiple planning sessions as a system component, while the participant manager handles agent registration where agents must announce their URL and capabilities to the platform before joining.

- The platform supports both human and agent participants, with humans interacting through a UI that abstracts the underlying protocol.

# Session Workflow and Phase Design

- The session follows five phases: (1) backlog presentation, (2) prioritization, (3) task assignment, (4) confirmation, and (5) summary distribution.

- Phase 2 involves two distinct prioritization types: business prioritization from the product owner's perspective, and technical prioritization where developers use dot voting with a limited number of dots to indicate which items should take precedence based on technical considerations.

- A significant gap was identified between prioritization and task assignment — a distinct sprint backlog formation step is needed where the team selects which items from the prioritized product backlog will be committed to the sprint, before assigning those selected items to individuals.

- Conversation and discussion need to be integrated across phases 1 through 4, not just later phases — even during backlog presentation, developers should be able to ask clarifying questions about features and tasks before moving to prioritization.

- The current implementation has the functional flow working with hardcoded deterministic behavior, with plans to add agentic reasoning and conversational capabilities on top of the working flow.

# Agent Capabilities, Knowledge Scoping, and Multi-Agent Differentiation

- All agents participating in a sprint planning session must have project-specific knowledge — they cannot be random agents without context about the project being planned, as they need to be stakeholders working on the same program.

- Agents are differentiated through responsibility rather than fundamentally different knowledge bases, analogous to how human developers may focus on different microservices or features (e.g., shopping cart vs. user profiling) while sharing general architectural understanding of the overall system.

- Responsibility can be divided horizontally (front-end vs. back-end) or vertically (by feature/service area), with overlap in shared project knowledge being acceptable and expected, mirroring how human team members operate.

- The discussion acknowledged that while agents share the same project information and thus have significant knowledge overlap, the multi-agent architecture is still necessary because agents represent different responsibilities, skill sets, and domains — the details of how to implement this differentiation is a separate implementation conversation.

- Core agent capabilities identified include: understanding and discussing backlog items in sprint planning context, asking for clarification, prioritizing items from a technical perspective, and performing task assignment.

# Task Assignment Mechanisms and Resource Constraints

- The current task assignment mechanism uses a first-come-first-served approach, with conflicts resolved by assigning to the agent with lower current workload, analogous to human velocity-based sprint commitment.

- Quantifying agent workload is an open research question, with proposed approaches including measuring by token usage, differentiating by model size (smaller vs. larger LLMs), and considering LLM budget constraints of the organization.

- Task complexity could be matched to agent capability — simpler tasks assigned to agents with smaller models (lower cost), complex tasks to agents with larger models (higher intelligence), reflecting both technical and business optimization.

- Designing algorithms for prioritization consensus (e.g., resolving different rankings across agents), sprint backlog selection, and task assignment were identified as core research contributions that distinguish this work from pure implementation.

- Two mechanisms need to be designed: one for fully autonomous agent-only planning, and another for mixed human-agent collaboration, each requiring different conflict resolution approaches.

# Evaluation Strategy and Ethics Approval Timeline

- Two evaluation tracks were identified: agent-only simulation where metrics are measured on autonomous planning outcomes, and human evaluation studies requiring participant interaction with the platform.

- Defining metrics for what constitutes a good versus bad planning session outcome is a key challenge that needs to be addressed, with the acknowledgment that this is where the research contribution lies.

- The ethics approval application needs to be locked in by the following week, as finalizing the human evaluation questionnaire and application early will free up time to focus on platform building and simulation.

- The questionnaire can leverage similarity to the prior estimation study, asking comparable questions since estimation is part of the planning process, though it still needs to go through a fresh approval process.

- The supervisor reiterated that the ambitious scope was flagged early as potentially not feasible within two months, reinforcing the urgency of finalizing evaluation plans and beginning execution immediately.
